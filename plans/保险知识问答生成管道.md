# 保险知识问答生成管道 · 最终优化方案

> 版本：v4.0（最终合并版） | 日期：2026-05-17
>
> 本方案整合了管道架构分析、工程落地建议与产品对比能力设计，形成可直接执行的优化计划。
> 核心定位：当前仓库是 **离线保险 QA 语料生产管道** ，优化目标是产出更安全、可检索、可路由、可比较的数据底座，为下游在线客服 / RAG 服务做准备。

---

## 一、现状评估与核心判断

### 1.1 管道现状

| 维度       | 现状                                                | 评价            |
| ---------- | --------------------------------------------------- | --------------- |
| 文档预处理 | PDF/DOCX 智能分块 + LLM 分类（47 险种 schema 约束） | ✅ 完善         |
| 种子生成   | 基于 chunk 的 LLM 生成，并发 20，断点续传           | ✅ 完善         |
| 种子去重   | embedding 前置去重，节省 ~46% 扩展 token            | ✅ 完善         |
| 批量扩展   | 改述 ×5 + 追问链 ×4 + 模板驱动 + 跨险种对比       | ✅ 基本完善     |
| 质量检查   | 格式校验 + 增量去重 + 规则事实校验 + 覆盖率分析     | ⚠️ 有优化空间 |

### 1.2 核心短板

1. **敏感场景边界未划清** ：核保结论、保费计算等不应由 LLM 自由生成的场景，无拦截和路由机制
2. **答案事实可靠性** ：扩展阶段答案无回溯校验，事实校验规则库仅覆盖 3 类硬事实
3. **产品级标识缺失** ：仅有险种大类，无法支持产品级路由和对比
4. **产品对比不可靠** ：当前 `CROSS_COMPARISON_PAIRS` 直接把 chunk 扔给 LLM 自由对比，缺乏参数化中间层，容易混淆产品细节或编造数字
5. **客户场景覆盖不足** ：保全变更、拒赔争议、健康告知等高频场景缺失
6. **元数据粗粒度** ：`business_stage` 沿用全业务链条而非客服视角，字段无枚举约束

### 1.3 关键决策

| 决策项   | 结论                                                        |
| -------- | ----------------------------------------------------------- |
| 项目定位 | 离线 QA 语料生产管道，不是在线客服系统                      |
| 本轮主线 | "工具路由边界"是最有价值的结构升级                          |
| 代码框架 | 现有结构足以承载所有改动，无需重写                          |
| 阶段建模 | 收敛为客服场景，不做内部经营流程建模                        |
| 答案核验 | 分层策略（规则锚点 → 高风险子集 LLM verify），不做全量核验 |
| 产品对比 | 参数抽取 → 结构化比较 → 自然语言渲染，不做自由对比        |
| 在线验证 | 补最小只读接口验证召回与路由，不做完整 Agent 编排           |

## 二、架构性原则

### 2.1 LLM 生成 vs 工具路由

| 判断维度   | 适合 LLM 生成 | 必须工具路由                   |
| ---------- | ------------- | ------------------------------ |
| 出错后果   | 体验下降      | 决策失误                       |
| 答案稳定性 | 可有不同表述  | 同一输入必须同一结果           |
| 数据敏感性 | 公开条款解读  | 商业机密（核保规则、精算数据） |
| 计算复杂度 | 无需精确计算  | 涉及公式、费率表               |
| 法律风险   | 一般性科普    | 可能被视为承诺                 |

**✅ LLM 生成：** 条款解释、流程指引、产品对比（保障范围层面）、注意事项、误解纠正

**🔧 工具路由：** 核保/健康告知、保费计算、现金价值/退保金、理赔金额计算、分红/万能账户、保单状态查询

### 2.2 证据优先、未知优先

这是贯穿全方案的通用原则，不只限于产品对比：

> **有明确文档证据才赋值；只有行业经验、没有文档证据时一律标"未知"。**

具体约束：

| 字段                | 允许赋值的条件                                       | 禁止的做法                           |
| ------------------- | ---------------------------------------------------- | ------------------------------------ |
| `premium_pattern` | 文档中有明确费率机制描述（均衡保费/自然费率/趸交等） | 凭"这是重疾险所以一定是均衡保费"推断 |
| `cash_value`      | 文档中出现现金价值表、退保章节、明确条款             | 凭险种类型推断"有/无"                |
| `benefit_type`    | 条款中出现"给付/报销/津贴/账户/赔偿责任"等明确机制   | 凭险种经验硬推                       |
| `waiting_period`  | 文档中明确写出天数                                   | 凭"重疾险一般90天"填充               |
| `deductible`      | 文档中明确写出金额                                   | 凭"百万医疗通常1万"填充              |
| `product_name`    | 出现在正文标题或前 500 字                            | 从文件名猜测或取条款中提及的对比产品 |

此原则直接影响 `param_extractor.py` 的 prompt 设计、`quality_checker.py` 的校验逻辑、以及产品对比的参数抽取。

### 2.3 产出物分类

所有管道产出物显式分为 5 类，通过 `qa_category` 字段标记：

| 类别         | `qa_category`值            | 说明                             |
| ------------ | ---------------------------- | -------------------------------- |
| 普通知识问答 | `knowledge`                | 条款解读、流程指引等             |
| 工具路由型   | `tool_routed`              | 核保/保费/退保金等，安全引导回答 |
| 误解纠正型   | `misconception_correction` | "错误问法 → 温和纠偏"           |
| 产品对比型   | `product_comparison`       | 参数化对比，含结构化中间态       |
| 拒答/澄清型  | `refusal_or_clarification` | 知识库外问题拒答 / 模糊问题反问  |

下游 RAG 检索到候选后，根据 `qa_category` 选择不同处理策略：

* `knowledge` → 直接回答
* `tool_routed` → 调用工具
* `misconception_correction` → 优先展示纠偏答案
* `product_comparison` → 展示结构化对比
* `refusal_or_clarification` → 反问或拒答

## 五、P0 优化项详细方案

### 5.1 产品名称提取

在现有 `classify_document_with_llm` 中增加 `product_name` 字段，零额外 LLM 调用。

**修改 `prompts/classify_document.txt`：**

```
你是保险文档分类专家。请根据文件名和内容预览，从给定选项中选择最合适的文档类型和险种，
并从文档内容中提取完整的保险产品名称。

文件名：{file_name}

内容预览（前1500字）：
{text_preview}

【文档类型】必须从以下选项中精确选择一个：
{doc_types}

【险种】必须从以下选项中精确选择一个：
{insurance_types}

【产品名称提取规则】
- 从正文中找到完整的保险产品名称（含公司名、型号后缀如分红型、万能型）
- 例如："中意真爱久久养老年金保险（万能型）"
- 如果文档是法规/监管文件等不涉及具体产品的，返回空字符串
- 如果一份文档涉及多个产品，返回主要产品名称

规则：
- 如果文档涉及多个险种，选最主要的一个
- 险种无法判断时选"其他保险"
- 文档类型无法判断时选"未分类"

只返回 JSON，不要任何其他说明：
{{"doc_type": "...", "insurance_type": "...", "product_name": "..."}}
```

**修改 `src/doc_preprocessor.py`：**

```python
@dataclass
class TextChunk:
    # ... 已有字段 ...
    product_name: str = ""

def classify_document_with_llm(...) -> tuple[str, str, str]:
    # ... 已有逻辑 ...
    product_name = result.get("product_name", "").strip()

    # 锚定校验：必须出现在前 500 字
    if product_name and product_name not in text[:500]:
        logger.warning(f"product_name '{product_name}' 未在前500字出现，丢弃")
        product_name = ""

    cache[md5] = {
        "doc_type": doc_type,
        "insurance_type": ins_type,
        "product_name": product_name,
    }
    return doc_type, ins_type, product_name
```

透传：chunk、种子、扩展产物统一继承 `product_name`。

```python
def normalize_metadata(qa: dict) -> dict:
    """入库前统一归一化"""
    # business_stage
    stage = qa.get("business_stage", "通用")
    qa["business_stage"] = STAGE_NORMALIZE.get(stage, stage)
    if qa["business_stage"] not in VALID_BUSINESS_STAGES:
        qa["business_stage"] = "通用"

    # difficulty / question_type
    diff = qa.get("difficulty", "入门")
    qa["difficulty"] = {"入门级":"入门","进阶级":"进阶","专业级":"专业"}.get(diff, diff)
    if qa["difficulty"] not in {"入门","进阶","专业"}: qa["difficulty"] = "入门"
    if qa.get("question_type") not in VALID_QUESTION_TYPES: qa["question_type"] = "概念解释"

    # qa_category 推断
    if not qa.get("qa_category"):
        if qa.get("is_tool_routed"):           qa["qa_category"] = "tool_routed"
        elif qa.get("misconception"):          qa["qa_category"] = "misconception_correction"
        elif qa.get("comparison_type"):        qa["qa_category"] = "product_comparison"
        elif qa.get("requires_clarification"): qa["qa_category"] = "refusal_or_clarification"
        else:                                  qa["qa_category"] = "knowledge"

    # tool_routing 一致性
    if qa.get("tool_routing") and not qa.get("is_tool_routed"): qa["is_tool_routed"] = True
    if qa.get("is_tool_routed") and not qa.get("tool_routing"): qa["is_tool_routed"] = False

    # 默认值补全
    for field, default in [
        ("product_name",""), ("tool_routing",""), ("tool_params",{}),
        ("is_tool_routed",False), ("requires_clarification",False),
        ("misconception",""), ("qa_category","knowledge"),
        ("comparison_type",""), ("product_a",""), ("product_b",""),
        ("comparison_dimensions",[]), ("comparison_verdict",""),
        ("comparison_limitations",""),
    ]:
        qa.setdefault(field, default)

    return qa
```

### 5.4 工具路由安全校验

```python
def validate_tool_routing_safety(qa: dict) -> list[str]:
    if not qa.get("is_tool_routed"):
        return []
    issues = []
    answer = qa.get("answer", "")
    for pattern in [
        r"可以(?:投保|购买|买)", r"不能(?:投保|购买|买)",
        r"会被拒保", r"标准体承保", r"加费承保", r"除外承保",
        r"保费(?:为|是)\s*\d+",
        r"(?:退保金|现金价值)(?:为|是)\s*\d+",
        r"(?:能|可以)赔\s*\d+", r"一定(?:能|可以|不能)",
    ]:
        if re.search(pattern, answer):
            issues.append(f"工具路由型答案包含确定性结论: {pattern}")
    if qa.get("tool_routing") and not qa.get("tool_params"):
        issues.append("tool_routing 已设置但 tool_params 为空")
    return issues
```

### 5.6 最小在线验证接口

```python
@router_data.get("/qa/ask")
async def qa_ask(question: str):
    """最小检索 + 路由验证（只读）"""
    from src.data_reader import _iter_jsonl

    passed_file = BASE_DIR / "data" / "qc_results" / "qa_passed.jsonl"
    if not passed_file.exists():
        return {"candidates": [], "tool_routing": None}

    q_lower = question.lower()
    q_bigrams = {q_lower[i:i+2] for i in range(len(q_lower)-1)}

    scored = []
    for qa in _iter_jsonl(passed_file):
        target = qa.get("question", "").lower()
        t_bigrams = {target[i:i+2] for i in range(len(target)-1)}
        if not q_bigrams or not t_bigrams: continue
        score = len(q_bigrams & t_bigrams) / len(q_bigrams)
        if score > 0.3:
            scored.append((score, qa))

    scored.sort(key=lambda x: x[0], reverse=True)
    candidates = [qa for _, qa in scored[:5]]

    tool_routing = None
    if candidates and candidates[0].get("is_tool_routed"):
        tool_routing = {
            "tool": candidates[0]["tool_routing"],
            "params": candidates[0].get("tool_params", {}),
        }

    return {
        "question": question,
        "candidates": candidates,
        "tool_routing": tool_routing,
        "qa_categories": [c.get("qa_category","knowledge") for c in candidates],
        "total_candidates": len(scored),
    }
```

### 5.7 去重性能优化

预分配 numpy 数组替代 list append + np.stack，10 行改动：

```python
max_unique = len(baseline_qa) + len(new_qa)
dim = new_embs.shape[1]
unique_matrix = np.zeros((max_unique, dim), dtype=np.float32)
unique_count = 0

if base_embs is not None and len(base_embs) > 0:
    unique_matrix[:len(base_embs)] = base_embs
    unique_count = len(base_embs)

for i, (qa, emb) in enumerate(zip(new_qa, new_embs)):
    if unique_count == 0:
        unique.append(qa); unique_matrix[0] = emb; unique_count = 1; continue
    sims = unique_matrix[:unique_count] @ emb  # 切片，不重建矩阵
    if float(sims.max()) > threshold:
        duplicates.append(qa)
    else:
        unique.append(qa); unique_matrix[unique_count] = emb; unique_count += 1
```

### 6.3 产品对比能力升级

#### 6.3.1 问题

当前 `CROSS_COMPARISON_PAIRS` 的做法是把两个险种相关的 chunk 拼在一起扔给 LLM 自由对比，存在三个问题：

1. LLM 容易混淆两个产品的细节（把 A 的等待期说成 B 的）
2. 价格、退保金、核保等敏感维度的对比没有走工具路由，LLM 直接编数字
3. 没有结构化中间层，无法验证对比结论的准确性

#### 6.3.2 新流程：参数抽取 → 结构化比较 → 自然语言渲染

```
文档 chunks
    ↓
[extract_comparison_profile]     ← LLM 抽取，每文档一次
    ↓
doc_comparison_profiles.jsonl    ← 结构化对比画像
    ↓
[generate_product_comparison]    ← 参数化比较，规则 + LLM
    ↓
comparison_intermediate.jsonl    ← 结构化对比中间态
    ↓
[render_comparison_answer]       ← LLM 渲染自然语言
    ↓
product_comparison Q&A           ← 最终输出
```

#### 6.3.3 对比画像（comparison_profile）

扩展 `src/param_extractor.py`，新增 `extract_comparison_profile`，输出到 `doc_comparison_profiles.jsonl`。

每份文档产出一个标准画像：

1. 产品定位

9. 是否建议组合配置

## 七、P2 优化项详细方案

### 7.1 分层答案回溯校验

**第一级（零 LLM 成本）：** 用 `source_chunk_id` 回查原始 chunk，检查答案中的数字是否出现在原文中。

```python
def anchor_verify(qa, chunks_index):
    issues = []
    answer = qa.get("answer","")
    chunk_id = qa.get("source_chunk_id","")
    if not chunk_id or chunk_id not in chunks_index: return []
    source_text = chunks_index[chunk_id]
    for m in re.finditer(r"(\d+(?:\.\d+)?)\s*(万)?\s*(元|天|日|年|%|个月)", answer):
        if m.group(0) not in source_text:
            issues.append(f"'{m.group(0)}' 未在来源 chunk 中找到")
    return issues
```

**第二级：** 仅对高风险条目（第一级发现疑似问题 + 追问链第 3 轮以上 + 答案含多个数字引用）做 LLM verify。预计 ~5% 条目，成本 ~¥15。

不对工具路由型条目做回溯校验（答案是固定模板，无需核验）。

## 十二、风险与约束

1. **工具路由安全红线** ：`validate_tool_routing_safety` 强制拦截。答案模板需经法务审核。
2. **证据优先强制执行** ：comparison_profile 中无证据的字段一律"未知"，prompt 中明确禁止凭经验推断。宁可少填，不可错填。
3. **产品对比范围控制** ：本轮只做白名单高频组合，不做任意两产品开放式自动比较。
4. **答案回溯成本** ：P2 的 LLM verify 仅对 ~5% 条目触发，成本 ~¥15。
5. **product_name 准确性** ：前 500 字锚定校验兜底，首批人工抽检。
6. **向后兼容** ：所有新增字段均有默认值，旧数据无需重新处理。
7. **不做的事** ：不做完整在线 Agent 编排、不做任意产品开放式对比、不做全量历史法规时点问答、不做全量 LLM 回溯核验。
